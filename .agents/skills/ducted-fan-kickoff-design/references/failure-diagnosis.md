# 失败诊断树

> 每条格式：**现象 → 先查什么 → 常见根因 → 处置 → 禁止的"绕过去"做法**
> 只写已被实际观察到、或已在阶段技能里固化的失败模式。

---

## F-001 AutoGrid 报 geomTurbo 格式错误

**现象**：打开 `.geomTurbo` 时报格式错误，但文件用文本编辑器看结构正常。

**先查**：**完整路径里有没有非 ASCII 字符（中文、全角字符）**。

**根因**：NUMECA 在非 ASCII 路径下会把合法文件误报为格式错误。

**处置**：把工程整体移到纯 ASCII 路径再试。

**禁止**：改文件语法、重排行序、手工"修"坐标——那会引入真正的格式错误。

**来源**：`axstream-airfoil-openfoam/SKILL.md` 报告规则

## F-002 FINE 点 Run 没反应 / 起不来

**现象**：点了 Run 没进程，或进程瞬间退出。

**先查**（按顺序）：
1. **授权**：`preflight.py numeca` —— license 特性是否可用
2. **MPI**：是否用了 MPI 启动器
3. **注册表 / SMPD**：旧 MPICH/SMPD 启动器会报注册表访问错误

**根因**：**分区成功 ≠ MPI 能跑。**

**处置**：用**同一个 `.iec`** 重新物化一个**未分区**的 `.run`，再顺序启动。
匹配求解器的 Intel MPI 2018 启动器已在 4500 rpm 实际验证过（8 计算进程 + 1 主进程）。

**禁止**：只给**分区后**的 `.run` 加 `-seq` 硬试——它仍可能读取并行配置。

**来源**：`numeca-cli-automation/SKILL.md` 实现说明；`v7/README-CFD.md`

## F-003 `finebatch -parallel` 生成的是 `.bat` 不是 `.batch`

**现象**：脚本按 `.batch` 找文件找不到。

**根因**：Windows FINE 16.1 的 `finebatch -parallel` 生成 `.bat`，且内容含 `-machinefile unknown`。

**处置**：按实际扩展名处理；`-machinefile unknown` 说明并行配置未真正生效，回到 F-002 的顺序路线。

**来源**：`numeca-cli-automation/SKILL.md`

## F-004 `Imax inconsistent` 警告

**现象**：`finebatch` 报块尺寸不一致。

**先查**：最终 `.run` 的块数、块名、每块 `IMAX/JMAX/KMAX` 与**新网格**基准是否完全一致。

**根因**：用旧网格的 `.run` 迁移到新网格，或只替换了 `GRID_FILE`。

**处置**：用新 `.igg` **重新物化** `.run`，逐块核对；从 `.std` 再确认 EURANUS 实际读取的新网格。

**禁止**：把"求解器能启动"当作新网格绑定正确的证明。

**来源**：`numeca-fine-solver/SKILL.md`「旧参数迁移到新网格」

## F-005 转子"落后角"达到 −70°…−140°

**现象**：后处理算出的转子落后角在 −70° 到 −140° 之间。

**先查**：**符号合同**，不是流动分离。

**根因**：把 NUMECA 相对出口气流角与 AutoBlade `CAMBER_BETA2` 直接相减，
而两者对转子采用**相反的周向正方向**。

**处置**（已验证合同）：
```
转子：delta_r = beta2 + CAMBER_BETA2
静子：delta_s = alpha2 − CAMBER_BETA2
```
映射后仍超过约 30° 再结合回流率、速度矢量、尾迹、端壁分离诊断。

**禁止**：直接解释成失速或大分离。

**来源**：`memory.md#2026-08-12`（C-005）

## F-006 末段质量流量持续振荡不衰减

**现象**：求解很久，出口流量在几个百分点范围反复摆，振幅不衰减。

**先查**：窗口均值、波动包络、采样收敛、残差位置。
**不能把伪时间迭代均值冒充物理时间平均。**

**判定**（本项目合同）：至少运行 30 分钟，末 **4×500** 连续细网格迭代两端均有 **≥1%** 的
反复振荡，各窗口振幅一致且不衰减、均值无明显漂移 → 保存退出，
原因 `persistent_flow_oscillation`，状态 `rejected`。

**处置**：保留原始 CGNS、STD 与 ICE 历史；诊断写入该工况的
`oscillation_diagnosis.json` 与 `oscillation_monitor.json`；独立转速线继续推进。

**禁止**：
- 把该点称为"已证实的失速边界"（稳态曲线区分不了数值非定常与物理非定常）
- 把它当作其他工况的重启动源
- 降 CFL 后直接宣布通过（降 CFL 是**待验证的数值诊断**，需独立 computation 保留对照）

**来源**：`v7/README-CFD.md`「持续振荡的提前保存退出」；`automation/oscillation_policy.json`

## F-007 质量流量与目标差很多 / `UNABLE TO RESPECT THE MASS FLOW`

**现象**：质量流量出口工况达不到目标。

**先查**：
1. 最终 `.run` 中 `REAL_ENTRY mass-flow` 的**有效命中数应为 1**
2. 它必须位于 `TYPE OUTLET` 块内（不能只搜到同名字符串）
3. 记录改前值、改后值、行号、边界索引、目标单位

**处置**：求解进入迭代后检查 `.std` 的 `MF_OUT` 是否稳定体现目标值
（`MF_IN` 在重启动初期可以暂时偏离）。

**禁止**：`UNABLE TO RESPECT THE MASS FLOW` 出现在**有效迭代之后**、或最终 `MF_OUT`
持续不满足目标时，把状态标为成功。

**来源**：`numeca-fine-solver/SKILL.md`「边界条件修改与硬核对」

## F-008 CFView 返回 0 但目标文件缺失/为空/时间戳未更新

**现象**：宏"成功"退出，但没出图。

**根因**：**CFView 在宏失败时仍可能返回退出码 0。**

**处置**：同时检查 CFView 日志与目标文件三件事（存在、非空、时间戳已更新）。

**禁止**：只看退出码就宣布出图成功。

**来源**：`numeca-cfview-post/SKILL.md`「适用假设与失败规则」

## F-009 功率闭合失败

**现象**：轴功率 ≠ 流体总焓升功率。

**这是复核信号，不是结论。** 按顺序查：
1. 周期扇区对不对
2. 叶片数缩放对不对
3. 扭矩定义（是不是用了 `allwalls`，见 C-001）
4. 站位总温取法

**禁止**：直接判定"算例物理质量差"。

**来源**：`numeca-fine-solver/SKILL.md` 强制原则 / C-001

## F-010 静推力不闭合

**现象**：`static_thrust ≠ momentum_thrust + pressure_thrust`。

**先查**：
1. 出口面积是否按**全周**算（CFView 周期扇区面积 × 出口叶排周期数）
2. 与轮毂/机匣半径解析的环面积交叉核验
3. 出口是否误用了转静接口或壁面

**处置**：**停止并报告**，不得回退到壁面轴向力。

**来源**：C-004

## F-011 `.iec` 里看不到刚算完的工况

**现象**：磁盘上有 `.run`，但 ICE 工程列表里没有。

**根因**：`.iec` 是 computation 清单的**唯一真源**；外部复制 `.run` **不会**自动出现在 `.iec` 中，
反过来目录存在也不代表工程已包含该算例。

**处置**：在对应 `.iec` 中完成同名 computation 的新增/复制/重命名/删除，
**保存并重新打开验证**；双向核对工程登记项与磁盘 `.run`。

**禁止**：把"目录存在"写成"工程已包含该算例"。

**来源**：`numeca-fine-solver/SKILL.md` 强制原则 8–9

## F-012 CFView/CGNS 读取冲突或最终解损坏

**现象**：`H5Dwrite` 失败，最终解损坏。

**根因**：Windows 16.1 原生 CGNS 写入可能与在线 HDF5 读者冲突。

**处置**：运行时**优先只读 STD/RES**；场后处理使用已完成且**已关闭**的输出，
或经验证的同步快照。

**禁止**：一边跑一边读 CGNS 做后处理。

**来源**：`numeca-fine-solver/SKILL.md`

---

## F-013 重启后残差基准重置

**现象**：重启后残差曲线从高的地方重新开始，看起来"退步了"。

**根因**：重启会重置显示残差基准。

**处置**：跨运行比较时必须明确**同一参考量**；仅有稀疏或其他算例的标签记录，
不能冒称当前算例的连续末段收敛。

**来源**：`numeca-fine-solver/SKILL.md`

## F-014 在 `D:\Project\Research` 或更上层出现了 `.git`

**现象**：工作区 skill 突然全部消失，DSH 目录里看不到。

**根因**：DSH 的项目根 = **包含 `.git` 的最近祖先目录**。上层出现 `.git` 会让 projectRoot 上移，
`turtbo-agent/.agents/skills` 不再是项目级 skill 根。

**处置**：删掉上层的 `.git`（确认它不是另一个正经仓库），或把 skill 同步到用户根
（`scripts/sync_skills.ps1`，需提权）。

**预防**：`tools/preflight.py` 每次校验 `projectRoot === cwd`。

**来源**：`@deepseek-ai/dsh-skill-filesystem/lib/index.js`；本仓库 README

## 诊断的通用顺序

遇到任何报错，先按这四问过一遍，再进具体条目：

1. **路径对吗？**（ASCII、存在、同名）
2. **身份对吗？**（哈希/块签名/网格版本是否指向你以为的那个文件）
3. **状态词对吗？**（已准备 / 已排队 / 正在运行 / 已正常退出 / 已验收——现在是哪一个）
4. **判据写了吗？**（没有判据的结论一律无效）
